== v0.6.1 — 2026-06-01 — CFF parser (read-only, palier 1/4)

=== Added

* **CFF (Compact Font Format) read-only parser** — first palier of
  the native OTF subsetting work (cf.
  `roadmap_pdf_cff_subsetting.md`). The new `PDF::Fonts::CFF::Parser`
  reads the Adobe CFF structure embedded in OpenType `.otf` files
  into in-memory objects :
+
--
** `CFF::Index` — generic INDEX reader (Name, Top DICT, String,
   Global Subr, CharStrings, Local Subr, FDArray).
** `CFF::Dict` — DICT operand/operator decoder (short int, 2-byte
   int, BCD real, 1- and 2-byte operators).
** `CFF::Parser` — orchestrator. Detects CIDFonts via `/ROS`, reads
   the Top DICT, CharStrings, Private DICT, Local Subrs, plus FDArray
   / Private / Local Subrs / FDSelect for CIDFonts.
--
+
**No modification of CFF data yet** — this palier is read-only.
Subsequent paliers (0.6.2 : Type 2 analyser ; 0.6.3 : subsetter ;
0.6.4 : `TrueTypeFont.load(.otf)` wiring) will build on top.

=== Validated against

* `/System/Library/Fonts/LastResort.otf` (2.5 KB, non-CID CFF) —
  spec'd as an integration test.
* `NotoSansCJKsc-Thin.otf` (15 MB, CIDFont with 65 535 glyphs,
  2342 global subrs, 19 FDs) — parsed cleanly in a manual smoke
  test.

== v0.6.0 — 2026-06-01 — J1 milestone closure

This release closes milestone **J1** of the ISO PDF trajectory
(cf. `doc/RATIONALE.adoc`). The shard now generates documents that
exercise every prerequisite of PDF/A-2b / PDF/A-3 :

* Calibrated colour management (OutputIntent + ICCBased — v0.5.8)
* Interactive forms with signatures, custom appearances and extended
  flags (AcroForm — v0.5.7 to v0.5.10)
* File attachments (Embedded files — v0.5.11)
* Modern cross-reference encoding (XRef streams — this release)
* Compressed objects (Object streams — this release)
* Spot / multi-channel colour (Separation, DeviceN — this release)

The next milestone (J2 — Tagged PDF / structure tree) starts from
the same code base.

=== Added

* **Cross-reference streams (`/Type /XRef`).** New
  `Document#xref_format = :stream` switches from the classic
  `xref ... trailer ... %%EOF` block to a Flate-compressed
  cross-reference stream (PDF 1.5+). The stream dict carries the
  trailer entries (`/Size`, `/Root`, `/Info`, `/Encrypt`, `/ID`,
  `/W`) and the binary entry table.

* **Object streams (`/Type /ObjStm`).** New
  `Document#object_streams = true` groups every compressible
  indirect (dict, array, name, number, string, boolean, null) into
  a single Flate-compressed ObjStm. Streams stay standalone.
  Activating object streams forces `xref_format = :stream`
  (type-2 cross-ref entries are required to reference compressed
  objects).

* **Separation colour space.** `PDF::ColorSpaces::Separation` —
  spot inks (Pantone, Cutter, etc.) with an `ICCBased` fallback
  and a Type-2 linear tint transform. Compatible with PDF/A-2b
  when paired with FOGRA39.

* **DeviceN colour space.** `PDF::ColorSpaces::DeviceN` — N-channel
  spot or process colour. MVP tint transform sums per-component
  contributions ; production usage should provide a
  FunctionType 4 tint for accuracy.

=== Changed

* Writer rewritten to support three operating modes : classic table
  (`xref_format = :table`), xref stream (`:stream`), and xref stream
  + object streams (`object_streams = true`).
* Documents with object streams are typically 8-20 % smaller than
  the same documents in classic mode. The exact gain depends on
  the number of compressible indirects.

== v0.5.11 — 2026-06-01

=== Added

* **Embedded files — Phase 2 of the ISO PDF trajectory (J1).**
  PDF documents can now carry arbitrary attached files (PDF spec
  § 7.11), unlocking PDF/A-3 conformance and Factur-X / ZUGFeRD
  electronic invoices.
+
[source,crystal]
----
pdf.attach_file(
  path: "factur-x.xml",
  description: "Factur-X invoice data",
  relationship: :data,        # PDF/A-3 § 6.8
  mime_type: "application/xml",
)
----

* **`PDF::EmbeddedFile`** — wraps the raw bytes plus a `/Params`
  dict carrying `/Size`, `/CreationDate`, `/ModDate` and a 16-byte
  MD5 `/CheckSum` (PDF spec § 7.11.4). The stream is Flate-compressed.

* **`PDF::FileSpec`** — file specification dict with `/F` (PDFDocEncoding
  name), `/UF` (UTF-16BE name), `/Desc`, `/AFRelationship` and an
  `/EF` sub-dict pointing at the embedded stream.

* **Seven `/AFRelationship` values** : `:data`, `:source`,
  `:alternative`, `:supplement`, `:unspecified` (PDF/A-3 § 6.8) plus
  `:encrypted_payload` and `:form_data` (PDF 2.0 additions).

* **`examples/factur_x.cr`** — end-to-end demo producing a PDF with
  a Factur-X-style XML stub embedded in `/AFRelationship /Data`.

=== Changed

* `PDF::Document#attach_file` accepts `path:`, `bytes:` or `io:`.
  At write time the catalog gets both `/AF` (PDF 2.0 + PDF/A-3
  required) and `/Names /EmbeddedFiles /Names` (PDF 1.x legacy
  expected by Acrobat, Preview and pdfdetach).

== v0.5.9 — 2026-06-01

=== Added

* **Signature field (`/FT /Sig`)** for the AcroForm module. New
  `PDF::AcroForm::SignatureField` declares a slot for a digital
  signature ; the cryptographic payload itself is filled later by
  `aloli-crystal/pdf-signature`. Adding any signature field
  automatically sets `/SigFlags 3` on the `/AcroForm` dict.
+
[source,crystal]
----
form.signature_field("contract", page: page, x: 100, y: 100, width: 200, height: 80)
----

* **Custom appearance streams for checkbox and dropdown** — both
  field types now ship a Form XObject in `/AP /N` that draws the
  field's frame and (for checkbox) its checked-state cross. This
  removes the dependency on `/NeedAppearances true` for visibility,
  which historically misbehaved on Preview macOS for these field
  types.

* **Custom appearance stream for text fields** — `/Tx` widgets now
  carry an `/AP /N` Form XObject that draws the field frame and
  the current value (or default value) using the embedded Helvetica
  font. Password fields render their value as masking asterisks
  (`*` per character). Auto-sized text (60 % of field height,
  clamped between 8 and 24 pt) ; multi-line uses fixed 12 pt with
  the baseline near the top of the field.

=== Changed

* `PDF::Document` exposes `acroform_helvetica_ref` — a cached
  indirect reference to the embedded Helvetica Type1 dict, shared
  by `/AcroForm /DR /Font /Helv` and by every text-field appearance
  stream so the font lives as a single object.

== v0.5.8 — 2026-06-01

=== Added

* **OutputIntent + ICCBased colour space (first step of J1 in the
  ISO PDF trajectory).** New module `PDF::OutputIntent` lets a
  document declare a calibrated output condition, a prerequisite
  for PDF/A-2b / PDF/A-3 conformance.
+
[source,crystal]
----
pdf.output_intent = PDF::OutputIntent.srgb     # default RGB
pdf.output_intent = PDF::OutputIntent.fogra39  # European CMYK offset
----
+
The bundled output intents reference two ICC profiles embedded in
the shard under `src/pdf/data/icc/` :
+
--
** **sRGB v4 ICC preference** (60 KB) — public domain, from the
   International Color Consortium registry.
** **Coated FOGRA39 / ISOcoated_v2_eci** (1.7 MB) — free for use
   per ECI download terms ; attribution preserved in
   `src/pdf/data/icc/LICENSE.adoc`.
--

* **`PDF::ColorSpaces::ICCBased`** — first concrete entry in the
  `ColorSpaces` namespace. Auto-detects the number of components (1
  Gray, 3 RGB, 4 CMYK) from the ICC profile header. Factory methods
  `.srgb_v4`, `.fogra39`, `.from_file(path)`.

=== Changed

* `PDF::Document#output_intent=` is the public setter. When set,
  `Document#finalize!` writes `/OutputIntents [...]` in the catalog
  alongside an indirect `OutputIntent` dict whose
  `/DestOutputProfile` points at a Flate-compressed stream carrying
  the ICC bytes.
* Shard size increases by ~1.8 MB to include the two ICC profiles.
  This is the acceptable trade-off chosen in `doc/RATIONALE.adoc`
  (point ouvert n°1, tranché 2026-06-01) to keep generated PDFs
  self-contained without any external file lookup at runtime.

== v0.5.7 — 2026-06-01

=== Added

* **Interactive AcroForm support (J0 of the ISO PDF trajectory).** New
  `PDF::AcroForm` module that produces fillable forms in Acrobat Reader,
  Preview macOS, Firefox PDF.js and Chrome. Five field types are
  supported in this first iteration :
+
--
** **Text** (`/FT /Tx`) — single- and multi-line, with `MaxLen`,
   `Password`, `Multiline`, alignment, default/initial value.
** **Checkbox** (`/FT /Btn` without `Pushbutton`/`Radio` flags) —
   `/Yes`/`/Off` states, with default state.
** **Radio group** (`/FT /Btn` with `Radio` flag) — kid widgets share
   `/Parent`, each carries `/AP /N` with native Form XObjects (empty
   ring for "off", ring + filled center dot for "selected") so the
   buttons are visible on every viewer. Without `/AP` Acrobat and
   Preview render nothing for radio kids ; without `/Parent` they
   ignore the kids entirely.
** **Dropdown / combo box** (`/FT /Ch` with `Combo` flag) — accepts
   either `Array(String)` (value = label) or `Hash(String, String)`
   (export value ⇒ display label), per PDF spec § 12.7.4.4.
** **Listbox** (`/FT /Ch` without `Combo` flag) — multi-line choice
   without dropdown.
--
+
DSL :
+
[source,crystal]
----
pdf.acroform do |form|
  form.text_field("nom", page: page, x: 100, y: 700, width: 200, height: 20)
  form.radio_group("genre", page: page, options: ["M", "F"], x: 100, y: 600)
  form.dropdown("pays", page: page, options: {"FR" => "France"}, x: 100, y: 550, width: 120, height: 20)
end
----
+
This MVP relies on `/NeedAppearances true` for text/checkbox/dropdown
appearance streams (the viewer regenerates them on fill). Custom
appearance streams across all field types will come in J1.

* **`doc/RATIONALE.adoc`** — substantive design document for the ISO
  PDF trajectory of this shard over the next 18-24 months : pragmatic
  ambition (ISO 32000-1 + PDF/A-2b/3b + PDF/UA-1 + PDF 2.0 crypto
  extensions), planned split into four shards (`pdf`, `pdf-a`, `pdf-ua`,
  `pdf-validate`), five milestones (J1-J5), declarative validator
  inspired by veraPDF. Out of scope assumed : PDF/X, PDF/E, PDF/VT.

* **`examples/acroform.cr`** — end-to-end demo that exercises every
  field type. Generates `acroform_demo.pdf` (~8 KB) ready to open and
  fill in any of the four major viewers.

=== Changed

* `PDF::Document` exposes `#acroform(&)` and `#acroform?`.
* `PDF::Page` exposes `#add_annotation_ref` so AcroForm can attach
  pre-registered widget annotation references to `/Annots` without
  re-registering them.
* `Document#finalize!` now finalizes the AcroForm *before* the pages,
  so widget references land in the right `/Annots` arrays. Without
  this ordering the widgets exist as indirect objects but are never
  linked to a page.

== v0.5.5 — 2026-05-08

=== Fixed

* **Collision de clés `F<n>` dans `/Resources /Font` quand on mélange
  des polices Type1 et TrueType sur la même page.** Le rendu d'un
  texte Type1 ajouté APRÈS un TTF était **invisible** : le
  `font_resource_key` calculait l'index dans `@font_resources` SANS
  tenir compte des TTF déjà enregistrés dans `@truetype_font_resources`,
  produisant une clé `F<n>` qui collisionnait avec celle du TTF.
  Acrobat / pdfinfo / pdftotext interprétaient alors les bytes
  WinAnsi du Type1 comme des codes glyphes TTF et ne rendaient rien.
+
Cas réel : `crystal-asciidoctor-pdf` rendait un mot en
**bold-italic** (ex. `*_mécanique_*`) qui **disparaissait** du PDF.
Le thème par défaut de ce shard charge DejaVu Sans pour body / bold
/ italic mais **pas** pour bold-italic ; le rendu fallback sur
`Helvetica-BoldOblique` (Type1 standard), et la collision F<n> avec
le TTF DejaVu déjà actif rendait le mot invisible.
+
Fix : la clé `F<n>` est désormais assignée à l'enregistrement du
Type1 (formule unifiée avec celle des TTF :
`F#{font_resources.size + truetype_font_resources.size + 1}`) et
stockée dans `@font_resource_keys`. Plus de collision possible.
+
Spec d'intégration `font_key_collision_spec.cr` qui vérifie qu'un
PDF mélangeant TTF → Type1 → TTF produit deux clés distinctes dans
le content stream.

== v0.5.3 — 2026-05-07

=== Fixed

* **Pages vides après fusion d'un PDF normalisé Ghostscript.** Le
  parser ne savait résoudre les références indirectes `/Length`
  d'un content stream que via `@xref` (objets uncompressed). Quand
  le `/Length` pointait sur un objet **stocké dans un object stream**
  (PDF 1.5+, structure générée par défaut par `gs ≥ 9.x`), la
  longueur restait à 0 → on lisait 0 octets → la page apparaissait
  vide après fusion.
+
Cas réel : livret « 2026-05-08--messe-laguiole » avec une partition
chiffrée RC4 d'origine, normalisée via `gs` (selon le contournement
documenté), produisait un livret avec deux pages vides numérotées
mais sans contenu visible.
+
Fix : `parse_stream` consulte maintenant `resolve_compressed_object`
en fallback quand `@xref` ne contient pas l'objet référencé.

* Spec d'intégration ajoutée
  (`spec/pdf/integration/length_in_object_stream_spec.cr`) qui
  reproduit le scénario : génère un PDF, le passe par `gs`, vérifie
  que le reader retrouve bien le contenu sur les pages
  re-compressées avec `/Length` indirect compressé.

== v0.5.2 — 2026-05-07

=== Fixed

* **Le parser tentait de déchiffrer les chaînes du dict `/Encrypt`
  lui-même** lors d'un re-parsing forcé (pattern utilisé par
  `crystal-combine-pdf` quand il matérialise tous les objets
  d'un PDF chiffré pour la fusion). Spec § 7.6.2 : les strings
  du `/Encrypt` (`/O`, `/U`, `/OE`, `/UE`, `/Perms`) **ne sont
  jamais chiffrées** — leurs bytes ont leur propre sémantique
  (hash MD5/SHA-256, blob AES-256 chiffré avec une clé dérivée
  différemment). En tentant de les AES-déchiffrer avec la
  `file_key` + `obj_num`, on cassait OpenSSL avec un
  `bad decrypt` paddings PKCS#7.
+
Le parser mémorise désormais l'`encrypt_object_number` (l'objet
indirect qui porte le `/Encrypt`) et saute le déchiffrement
récursif pour ce seul objet.

== v0.5.1 — 2026-05-07

**Authentification owner pour V<5 et validation /Perms pour V=5.**
Complète la couverture du Standard Security Handler côté lecture.

=== Added

* **Algorithm 7** (PDF spec § 7.6.3.4) — authentification via le
  mot de passe owner pour V=1, V=2 et V=4 (R=2, R=3, R=4). Le
  reader essaie d'abord le mot de passe utilisateur, puis le owner.
+
[source,crystal]
----
# Fonctionne avec un PDF chiffré RC4-128 ou AES-128 par qpdf
# `--encrypt user-pwd owner-pwd 128 --use-aes=y`
reader = PDF::Reader.open("doc.pdf", password: "owner-pwd")
----

* **Algorithm 13** (ISO 32000-2 § 7.6.4.4.10) — validation du
  bloc /Perms après dérivation de la clé du fichier en V=5. Vérifie
  la signature "adb" (bytes 9..11), le marqueur 0xFFFFFFFF (4..7) et
  le drapeau /EncryptMetadata (byte 8).
+
Si /Perms a été altéré ou si la clé dérivée est fausse pour une
raison subtile (collision), `EncryptedPdfError` est levée. Couche
de défense supplémentaire en plus du check /U.

=== Tests

* Spec d'intégration : ouverture par mot de passe owner d'un PDF
  AES-128 R=4 et RC4-128 R=3 produits par qpdf.
* Spec de tampering : modification d'un caractère hex de /Perms
  → l'ouverture échoue désormais (avant : passait silencieusement).
* Suite globale : 807 examples, 0 failure.

== v0.5.0 — 2026-05-07

**Chiffrement et déchiffrement AES natifs** — le shard couvre
désormais l'intégralité du « Standard Security Handler » du
spec PDF (ISO 32000-1 et ISO 32000-2 § 7.6.4) pour la lecture
**et** l'écriture, sans dépendance externe.

Les trois niveaux modernes sont disponibles :

[options="header",cols="1,1,1,3"]
|===
|Niveau         | V/R  | Compatibilité       | Cas d'usage
|`:rc4_128`     | 2/3  | Acrobat ≥ 5 (1999)  | Legacy uniquement (RC4 cassé)
|`:aes_128`     | 4/4  | Acrobat ≥ 7 (2005)  | Bon compromis
|`:aes_256`     | 5/6  | Acrobat ≥ X (2012)  | PDF 2.0, défaut
|===

=== Added

* **Lecture des PDFs chiffrés AES** :
+
--
** AES-128-CBC (V=4, R=4 + CryptFilter `AESV2`) — utilisé par
   les exports Office récents et Acrobat ≥ 9.
** AES-256-CBC (V=5, R=6 + CryptFilter `AESV3`, ISO 32000-2) —
   PDF 2.0, Algorithm 2.B (cascade SHA-256/384/512 + AES-128
   sur 64+ rounds).
--
+
R=5 (transitoire, déprécié par Adobe avant publication d'ISO
32000-2) lève une `EncryptedPdfError` explicite avec un message
de contournement (`qpdf --decrypt` puis `--encrypt ... 256`).

* **Écriture de PDFs chiffrés** via `Document#encrypt(...)` :
+
[source,crystal]
----
pdf = PDF::Document.new
pdf.encrypt(
  user_password: "user",
  owner_password: "owner",
  permissions: [PDF::Security::Permission::Print],
  level: :aes_256, # :rc4_128, :aes_128 ou :aes_256
)
pdf.page do |page|
  page.font "Helvetica", size: 12
  page.text "Confidentiel", at: {72, 720}
end
pdf.save("encrypted.pdf")
----
+
Le `DocumentWriter` chiffre tous les streams ET toutes les
chaînes indirectes (`/Title`, `/Author`, etc.) au moment de
l'écriture, en utilisant la clé par-objet calculée selon
Algorithm 1 du spec.

* **`PDF::Encryption::AES`** — wrapper sur `OpenSSL::Cipher` pour
  AES-128/256 CBC. Quatre helpers : `encrypt`/`decrypt` (avec IV
  préfixé pour les streams) et `encrypt_no_iv`/`decrypt_no_iv`
  (sans padding ni IV pour /OE, /UE, /Perms en V=5).

* **Déchiffrement des chaînes indirectes** : le parser marche
  désormais le sous-arbre de chaque objet indirect non-stream et
  déchiffre les `Objects::Str` rencontrés. Indispensable pour lire
  correctement le `/Info` (`/Title`, `/Author`, `/Producer`) et
  les annotations textuelles dans un PDF chiffré.

=== Changed

* `Document#encrypt` accepte un nouveau paramètre `level:`
  (défaut `:aes_256`). L'ancien `key_length:` reste accepté
  mais mappe vers RC4 (le seul algorithme paramétrable par
  longueur de clé en bits).

* `PDF::Reader.open(path, password: "...")` accepte maintenant
  les V=4 (AES-128) et V=5 (AES-256). Le mot de passe owner
  fonctionne aussi via Algorithm 2.A (V=5 uniquement pour le
  moment ; V<5 owner password à venir).

=== Internals

* Nouveau module `PDF::Encryption` :
+
--
** `RC4` — chiffrement de flux RC4, ~50 lignes Crystal pur.
** `AES` — wrapper AES-128/256 CBC autour d'`OpenSSL::Cipher`.
** `StandardSecurity` — Standard Security Handler complet
   (`Algorithm 1, 2, 2.A, 2.B, 3, 4, 5, 8, 9, 10`) avec
   `enum Cipher { RC4, AES_128, AES_256 }` et
   `enum Level { RC4_128, AES_128, AES_256 }`.
--

* `Objects::Stream#replace_encoded!(bytes)` — méthode utilitaire
  pour le writer : remplace les octets ET persiste les noms de
  filtres dans le dict avant de neutraliser `@filters` (sinon le
  reader ne sait plus qu'il faut Flate-décoder après déchiffrement).

* `Objects::Str` : `value` et `hex` deviennent `property` (étaient
  `getter`) — nécessaire pour le déchiffrement et le chiffrement
  en place côté parser/writer.

=== Tests

* 27 nouveaux specs encryption (RC4, AES, intégration qpdf,
  round-trip, croisée pdftotext). Suite globale : 803 examples,
  0 failure.

== v0.4.0 — 2026-05-01

**Déchiffrement natif des PDFs chiffrés RC4** — le shard sait
désormais ouvrir et lire les PDFs protégés par le « Standard
Security Handler » V=1/V=2 (RC4 40 à 128 bits, R=2 et R=3),
sans dépendance externe.

=== Added

* **`PDF::Encryption::RC4`** — implémentation pure Crystal du
  chiffrement de flux RC4 (Rivest Cipher 4), couvrant le KSA et
  le PRGA. ~50 lignes, validée contre les vecteurs de test du
  RFC 6229 et de Wikipedia (`Key`/`Plaintext`,
  `Wiki`/`pedia`, `Secret`/`Attack at dawn`).
+
[source,crystal]
----
cipher = PDF::Encryption::RC4.new(key)
encrypted = cipher.apply(plaintext)
# RC4 est symétrique : apply(apply(data)) == data
----

* **`PDF::Encryption::StandardSecurity`** — Standard Security
  Handler conforme à ISO 32000-1 § 7.6.3 :
+
--
** Algorithm 2 — dérivation de la clé du fichier à partir du
   mot de passe utilisateur, du `/O`, du `/P` et du `/ID`.
   Cascade MD5 sur 50 itérations pour R≥3.
** Algorithm 4 (R=2) / Algorithm 5 (R=3) — validation du mot
   de passe contre le `/U`.
** Algorithm 1 — dérivation de la clé par-objet (MD5 du
   `file_key || obj_num_LE3 || gen_LE2`, tronquée à `n+5`).
--

* **`PDF::Reader.open(path, password = "")`** — accepte un
  paramètre `password` optionnel. Si le PDF n'est pas chiffré,
  le paramètre est ignoré ; sinon il est essayé contre le `/U`.
  Mot de passe vide par défaut (couvre le cas « owner-only »
  ultra-courant des PDFs Office / Acrobat avec restrictions de
  copie ou d'édition).

=== Changed

* **`PDF::EncryptedPdfError`** n'est plus levée dès qu'un PDF
  contient `/Encrypt`. Elle l'est uniquement quand :
+
--
** L'algorithme n'est pas supporté (V=4 avec CryptFilter
   AESV2, V=5 AES-256). Le message indique le contournement :
   `crystal-combine-pdf gs FICHIER.pdf -i --backup`.
** Le mot de passe utilisateur est invalide.
** Le dictionnaire `/Encrypt` est mal formé.
--

* `Parser` injecte maintenant la clé par-objet sur les flux
  ET les chaînes (objets indirects) au moment du parsing.
  Les flux sont déchiffrés AVANT décompression Flate, comme
  le veut le spec.

=== Roadmap

* **AES-128 R=4** (V=4 avec CryptFilter `Standard CFM=AESV2`) :
  utilisé par les exports Office récents et Acrobat ≥ 9. Effort
  estimé S (1-2 jours) — toute la mécanique de clé est déjà en
  place, il « suffit » de brancher AES-CBC à la place de RC4.
* **AES-256 R=5/R=6** (V=5) : exigé par PDF 2.0. Effort estimé
  M — la dérivation de clé change (SHA-256 + Unicode SASLprep),
  pas seulement le cipher.

=== Added

* **`PDF::EncryptedPdfError`** — exception dédiée levée par
  `Reader.open` quand le trailer contient `/Encrypt`. Les PDFs

  ne sont pas déchiffrés ; tenter de Flate-décoder des octets

== v0.3.6 — 2026-04-27

**Extended PDF compatibility: 1.5+ and undecoded streams.** Lifts
the blocker that prevented `Reader` from reading modern PDFs
produced by LilyPond, Microsoft Word, or any engine emitting xref
streams or CCITT/DCT images.

=== Added

* **`Parser#parse_xref_stream`** (PDF 1.5+, ISO 32000-1 § 7.5.8) —
  replaces the classic xref table with a stream object
  `/Type /XRef`. Format: `/W [w1 w2 w3]` (field widths in bytes),
  `/Index` (sub-sections), entries in big-endian. Three entry
  types supported:
  ** Type 0 (free object)
  ** Type 1 (in-use, `field2`=offset)
  ** Type 2 (compressed, `field2`=objstm number,
     `field3`=index in stream)
* **`Parser#resolve_compressed_object`** (PDF 1.5+, ISO 32000-1
  § 7.5.7) — reads an object stored in an object stream
  (`/Type /ObjStm`). Header `/N` + `/First` + pairs
  `obj_num offset_in_stream` + plain-text object values.
* **`Reader#resolve_reference`** automatically consults
  `Parser#compressed_objects` when an object number has no direct
  xref offset → PDF 1.5+ objects become transparent to callers.
* **`Parser`: PNG Predictor** (None/Sub/Up/Average/Paeth) applied
  after FlateDecode when `/DecodeParms /Predictor >= 10`.
  Required for xref streams.
* **`Parser`: ASCIIHexDecode and ASCII85Decode** are now fully
  decoded.
* **`Stream#decoded`** (`Bool`, default `true`) — flag indicating
  whether `data` contains decoded bytes (filters inverted) or raw
  encoded bytes (unsupported filter).

=== Changed

* **`Parser#decompress_stream`** now returns `Tuple(Bytes, Bool)`:
  if any filter is not invertible (CCITTFaxDecode, DCTDecode,
  JBIG2Decode, JPXDecode, LZWDecode, RunLengthDecode, Crypt), the
  parser keeps the ENCODED bytes and marks the `Stream` as not
  decoded. Copiers (mergers) MUST honour this flag: preserve
  `/Filter` and `/DecodeParms` at re-writing time when
  `decoded == false`.

=== Removed

* The noisy warning
  `"AVERTISSEMENT : stream xref détecté (PDF 1.5+), non supporté en v1"`
  that fired on every modern PDF. No more use: everything is read
  silently.

=== Tested

* 776 specs green (unchanged). Manual validation on a 16-PDF
  corpus (PDF 1.3 to 1.7, CCITTFaxDecode scans, DCTDecode JPEGs,
  LilyPond, MS Word, Finale, Sibelius): all read correctly.

== v0.3.4 — 2026-04-25

=== Fixed

* **Reading back PDFs amended via `add_content_stream`**.
  `PDF::Reader.open` crashed with `Invalid Int32: ""` (raised from
  `find_xref_offset`) when re-opening any PDF that contained a
  binary content stream — typically a stream with bytes ≥ 0x80,
  produced by `crystal-watermark`, `crystal-combine-pdf` and any
  other downstream library that appends content via the incremental
  update mechanism (PDF spec § 7.5.6).

  Root cause: `find_xref_offset` searched for `"startxref"` via
  `String#rindex`, which returns an offset in **characters** (UTF-8).
  As soon as a multi-byte UTF-8 sequence appeared in the search
  area (any byte ≥ 0x80 followed by a continuation byte), the
  character offset diverged from the byte offset, and
  `@pos = search_start + idx + 9` landed past the real `startxref`
  marker. `read_int` then read an empty string and crashed.

  Fix: scan the raw bytes directly via a new private
  `byte_rindex(haystack, needle, from)` helper. No interpretation
  of the bytes as UTF-8 — the search is purely byte-level and
  immune to the encoding of the surrounding content streams.

* New regression test in `spec/pdf/reader_spec.cr` ("réouvre un PDF
  amendé contenant des octets binaires (≥ 0x80)") that amends a PDF
  with a content stream covering the full byte range 0..255 and
  asserts `PDF::Reader.open` returns the correct page count.

== v0.3.2 — 2026-04-23

=== Fixed

* **SVG `Z` path command**: `renderer.cr` used `page.close_stroke` to
  terminate a subpath on `Z`, which emits the PDF `s` operator
  (close + stroke). That consumed the current path, so the
  subsequent call to `apply_fill_and_stroke` had nothing left to
  fill. Visually, closed SVG shapes rendered as thin outlines
  instead of filled colour regions — country flag SVGs in
  particular showed empty boxes instead of bands of colour. Switched
  to `page.close_path` (PDF `h` operator) so the path stays alive
  for the fill / stroke decision.

== v0.3.1 — 2026-04-23

=== Fixed

* **SVG `path_parser` tokenizer**: fix an infinite loop triggered by
  certain compact path-data strings. When a number ended with a `.`
  that was immediately followed by another `.` starting the next
  number (e.g. `4.4.8` or `3 0.5.7`, a pattern common in tightly
  packed flag SVGs), the inner number-parsing loop would break on
  the very same `.` it had just stopped at without advancing `i`,

  unconditionally consumes the first character of a numeric token.

  and a reduced extract of the Brazil flag path that used to hang.
